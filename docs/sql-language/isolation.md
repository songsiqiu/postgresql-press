# 事务隔离级别

事务隔离级别决定一个事务在并发情况下能看到什么。新手先不用背所有异常现象，先理解“越隔离，越安全，但并发成本可能越高”。

## 你学完能干什么

- 知道事务隔离解决什么问题
- 能理解为什么两个事务可能看到不同结果
- 能区分常见隔离级别的大致强弱
- 知道不要随便把隔离级别调到最高

## 为什么需要隔离级别

如果两个事务同时读写同一批数据，数据库要决定：

- 能不能看到别人未提交的数据
- 同一事务里两次查询结果是否必须一致
- 并发修改冲突时谁成功、谁失败

隔离级别就是这些规则的组合。

## 常见隔离级别

| 隔离级别 | 新手理解 |
| --- | --- |
| Read Committed | 每条语句只能看到已经提交的数据 |
| Repeatable Read | 同一事务里多次读取更稳定 |
| Serializable | 最严格，尽量像事务一个个排队执行 |

PostgreSQL 默认常见是 Read Committed。

## 一个简化例子

事务 A：

```sql
BEGIN;
SELECT balance FROM accounts WHERE id = 1;
```

事务 B 修改并提交了同一行后，事务 A 再查一次，能不能看到新值，就和隔离级别有关。

## 动手区：模拟两次读取

假设账户 `id = 1` 一开始余额是 `500`。

| 时间 | 事务 A | 事务 B |
| --- | --- | --- |
| 1 | `BEGIN;` | |
| 2 | 查到余额 `500` | |
| 3 | | `UPDATE accounts SET balance = 600 WHERE id = 1;` |
| 4 | | `COMMIT;` |
| 5 | 再查一次余额 | |

在 `Read Committed` 下，事务 A 第二次查询通常能看到已经提交的 `600`。

在 `Repeatable Read` 下，事务 A 更倾向于继续看到自己事务开始时的一致视图，也就是 `500`。

这个动手区要记住的不是死背表格，而是：同一事务里“第二次看见什么”，取决于隔离级别。

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| 隔离级别 | 并发事务之间互相能看到什么的规则 |
| 已提交 | 事务已经 `COMMIT` 的修改 |
| 并发异常 | 多个事务同时操作时出现的不符合预期现象 |
| 序列化 | 尽量让结果像事务按顺序执行 |

## 练习题

1. 隔离级别主要解决什么问题？
2. PostgreSQL 默认常见隔离级别是什么？
3. 隔离级别越高一定越好吗？
4. 为什么并发修改可能失败或需要重试？

::: tip 提示
隔离级别不是背概念，而是理解“事务之间看到彼此的程度”。
:::

::: details 答案
1. 解决并发事务之间的可见性和一致性问题。
2. Read Committed。
3. 不一定，更高隔离可能带来更多等待、冲突或性能成本。
4. 数据库要保护一致性，冲突时可能让某个事务失败。
:::

## 常见坑

- 遇到并发问题就直接调最高隔离级别
- 不理解默认隔离级别下同一事务里查询结果可能变化
- 事务失败后没有设计重试或错误处理

## 先记住这三句

- 隔离级别控制事务之间能看到什么。
- 更严格不一定更适合。
- 并发冲突要配合业务重试和错误处理。
