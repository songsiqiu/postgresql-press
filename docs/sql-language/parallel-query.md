# 并行查询

并行查询让 PostgreSQL 在合适场景下用多个工作进程一起完成一条查询。新手先理解：它是加速大查询的机会，不是每条 SQL 都会自动变快。

## 你学完能干什么

- 知道并行查询适合什么场景
- 能在执行计划里看出并行执行迹象
- 理解并行不是越多越好
- 能避免把并行当成索引和 SQL 优化的替代品

## 看执行计划

```sql
EXPLAIN
SELECT user_id, count(*)
FROM notes
GROUP BY user_id;
```

如果计划里出现 `Gather`、`Parallel Seq Scan` 这类节点，通常表示 PostgreSQL 正在考虑并行执行。

## 什么时候可能有用

- 表很大，需要扫描很多行
- 聚合或排序工作量明显
- 机器有足够 CPU 资源
- 查询本身适合拆给多个工作进程

小表、很短的查询、已经能精准走索引的查询，不一定适合并行。

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| 并行查询 | 多个工作进程一起执行一条查询 |
| `Gather` | 汇总并行 worker 结果的计划节点 |
| worker | 参与执行的工作进程 |
| 顺序扫描 | 按表数据顺序扫描行 |

## 练习题

1. 并行查询适合小表短查询吗？
2. 执行计划里看到 `Gather` 通常说明什么？
3. 并行查询能替代合适索引吗？
4. 机器 CPU 很紧张时，盲目提高并行度合适吗？

::: tip 提示
先用 `EXPLAIN` 看计划，再判断是不是并行真的帮上忙。
:::

::: details 答案
1. 通常不适合。
2. 查询计划里有并行结果汇总。
3. 不能。
4. 不合适，可能造成资源争用。
:::

## 常见坑

- 以为所有查询都会自动并行
- 把并行度调很高却不看 CPU 压力
- SQL 写得低效，却只想靠并行解决
- 不看执行计划就判断并行是否生效

## 先记住这三句

- 并行查询适合大查询。
- 执行计划能告诉你有没有并行。
- 并行不是索引和 SQL 优化的替代品。
