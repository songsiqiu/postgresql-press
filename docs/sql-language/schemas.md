# 模式与命名空间

模式是数据库里的分类目录。它能把表、视图、函数等对象分组，避免所有东西都堆在一个平面里。

## 你学完能干什么

- 知道模式和数据库、表的区别
- 能理解 `public` 模式是什么
- 能知道什么时候需要自定义模式
- 能看懂带模式名的表名

## 一个例子

```sql
CREATE SCHEMA app;

CREATE TABLE app.notes (
  id bigserial PRIMARY KEY,
  title text NOT NULL
);
```

这里的 `app.notes` 表示：`notes` 这张表在 `app` 模式下面。

查询时也可以写完整名字：

```sql
SELECT id, title
FROM app.notes;
```

## 和数据库、表的关系

| 层级 | 新手理解 |
| --- | --- |
| 实例 | 一套正在运行的 PostgreSQL 服务 |
| 数据库 | 一个相对独立的数据空间 |
| 模式 | 数据库里的分类目录 |
| 表 | 真正存放一类数据的结构 |

## 容易混淆的词

| 词 | 不要混成 |
| --- | --- |
| 数据库 | 不是模式 |
| 模式 | 不是表，也不是权限本身 |
| `public` | 默认常见模式，不代表所有人都应该随便写 |
| 命名空间 | 主要解决对象名称归属和隔离问题 |

## 练习题

1. `app.notes` 里的 `app` 是什么？
2. 模式和数据库是一回事吗？
3. 为什么大项目可能会拆多个模式？
4. 创建模式的 SQL 是什么？

::: tip 提示
先把模式理解成数据库里的文件夹，但它还会和权限、搜索路径相关。
:::

::: details 答案
1. 模式名。
2. 不是。数据库更大，模式在数据库里面。
3. 可以按业务、模块或权限隔离对象。
4. `CREATE SCHEMA app;`
:::

## 常见坑

- 把模式当成数据库
- 表在别的模式里，却只写表名导致找不到
- 默认都放在 `public`，后面对象越来越乱

## 先记住这三句

- 模式是数据库里的分类目录。
- `schema.table` 能明确对象位置。
- 大项目可以用模式隔离对象和权限。
