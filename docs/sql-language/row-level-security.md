# 行级安全策略

行级安全策略用来控制“同一张表里，不同用户能看到或修改哪些行”。它比普通表权限更细。

## 你学完能干什么

- 知道行级安全策略解决什么问题
- 能区分表权限和行权限
- 能理解为什么多租户系统常关注它
- 知道策略写错可能导致看不到数据或越权

## 普通权限和行级安全的区别

普通权限通常回答：

> 这个角色能不能查询这张表？

行级安全策略进一步回答：

> 这个角色能查询这张表里的哪些行？

## 一个简化例子

```sql
ALTER TABLE notes ENABLE ROW LEVEL SECURITY;

CREATE POLICY user_notes_policy
ON notes
USING (user_id = current_setting('app.current_user_id')::bigint);
```

这表示查询 `notes` 时，只能看到当前应用用户对应的行。

这里的例子是简化场景，真实项目需要严谨设计连接身份、会话变量和权限边界。

## 适合什么场景

- 多租户系统
- 用户只能看自己的数据
- 同一张表按组织、学校、部门隔离
- 希望数据库层也兜住行级访问边界

## 练习题

1. 行级安全策略控制的是表级权限还是行级可见性？
2. 为什么多租户系统可能需要它？
3. 策略写错可能带来哪两类风险？
4. 它能替代所有应用层权限判断吗？

::: tip 提示
行级安全是更细的数据库权限边界，但仍然要和应用层权限设计一起看。
:::

::: details 答案
1. 行级可见性和可操作范围。
2. 不同租户的数据通常在同表或同库中隔离，需要防止互相看到。
3. 看不到该看的数据，或看到不该看的数据。
4. 不能，应用层仍要做业务权限判断。
:::

## 常见坑

- 以为有表权限就等于能看到所有行
- 策略条件写错，导致数据全部不可见
- 把行级安全当成应用权限系统的完全替代品

## 先记住这三句

- 表权限管能不能碰表。
- 行级安全管能碰哪些行。
- 策略要小心验证，不能只写完就算。
