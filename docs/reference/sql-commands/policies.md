# CREATE POLICY 与 DROP POLICY 速查

`CREATE POLICY` 用来创建行级安全策略，`DROP POLICY` 用来删除策略。策略决定角色能看见或修改哪些行。

## 你学完能干什么

- 知道策略和行级安全有关
- 能看懂策略的基本结构
- 理解策略不是应用权限的全部替代
- 能避免启用策略后忘记测试角色视角

## 创建策略

```sql
CREATE POLICY notes_owner_select
ON notes
FOR SELECT
USING (owner_id = current_user_id());
```

这表示查询 `notes` 时，只允许看到满足条件的行。

删除策略：

```sql
DROP POLICY notes_owner_select ON notes;
```

策略通常要配合表上的行级安全启用一起理解。

## 适合场景

- 多租户数据隔离
- 不同角色只能看自己的数据
- 数据库层补一层行级保护
- 不适合替代所有应用权限逻辑

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| 行级安全 | 按行控制可见或可改范围 |
| 策略 | 具体的行过滤规则 |
| `USING` | 控制哪些行可见或可操作 |
| 角色视角 | 用某个角色实际能看到什么 |

## 练习题

1. `CREATE POLICY` 和行级安全有没有关系？
2. 策略通常控制列权限还是行范围？
3. 删除策略时需要指定表吗？
4. 策略能完全替代应用权限设计吗？

::: tip 提示
行级安全要用真实角色测试，不要只用管理员视角看。
:::

::: details 答案
1. 有。
2. 行范围。
3. 需要。
4. 不能。
:::

## 常见坑

- 只创建策略，忘记检查行级安全是否启用
- 用超级用户测试，误以为普通角色也一样
- 策略条件写得过宽或过窄
- 把数据库策略当成全部权限系统

## 先记住这三句

- 策略控制行范围。
- 行级安全要用角色视角测试。
- 数据库策略不能替代完整权限设计。
