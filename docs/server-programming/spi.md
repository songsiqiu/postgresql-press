# SPI 接口

SPI 是 Server Programming Interface，允许服务端函数在数据库内部执行 SQL。新手先知道：它是写扩展和底层函数时用的能力，不是日常应用连接数据库的接口。

## 你学完能干什么

- 知道 SPI 属于服务端编程能力
- 能区分 SPI 和普通客户端连接
- 理解它常见于扩展或 C 函数开发
- 能避免把它当成新手必学内容

## 一个直觉例子

普通应用通常这样访问数据库：

```text
应用代码 -> 数据库连接 -> 执行 SQL
```

SPI 更像是：

```text
数据库内部函数 -> SPI -> 执行 SQL
```

也就是说，SQL 是从数据库服务端内部发起的。

## 可照着理解：它不该出现在哪里

如果你是在写普通 Web 接口，通常路径应该是：

```text
应用 -> 驱动 -> PostgreSQL
```

如果你在写扩展或 C 服务端函数，才可能进入：

```text
PostgreSQL 服务端函数 -> SPI -> PostgreSQL 内部执行 SQL
```

所以遇到连接池、参数绑定、事务重试问题时，先看客户端接口，不要跳到 SPI。

## 什么时候会遇到

- 阅读 PostgreSQL 扩展开发资料
- 写 C 语言服务端函数
- 研究触发器或内部函数实现
- 看官方服务端编程章节的底层接口

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| SPI | 数据库内部执行 SQL 的服务端接口 |
| 客户端接口 | 应用从外部连接数据库的接口 |
| 扩展 | 给 PostgreSQL 增加能力的组件 |
| 服务端函数 | 在数据库内部运行的函数 |

## 练习题

1. SPI 是应用外部连接数据库的普通接口吗？
2. SPI 更常见于扩展开发还是普通 CRUD 页面？
3. SPI 发起 SQL 的位置在数据库内部还是应用外部？
4. 新手学习 SQL 时需要先深入 SPI 吗？

::: tip 提示
看到 SPI，先把它放到“服务端编程/扩展开发”这一类。
:::

::: details 答案
1. 不是。
2. 扩展开发。
3. 数据库内部。
4. 不需要。
:::

## 常见坑

- 把 SPI 和 JDBC、libpq 这类客户端接口混在一起
- 还没理解函数和扩展就直接钻 SPI
- 在数据库内部隐藏太多业务查询
- 忽略服务端函数里的权限和错误处理
- 把 SPI 当作应用连接性能优化手段

## 先记住这三句

- SPI 是数据库内部接口。
- 普通应用开发通常不用直接碰 SPI。
- 它属于服务端编程的进阶主题。
