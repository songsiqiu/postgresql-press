# 触发器设计

触发器能在数据变化时自动执行逻辑。它很强，但也容易把业务藏起来，让排查变难。

## 你学完能干什么

- 知道触发器适合哪些明确场景
- 能区分行级触发器和语句级触发器
- 知道触发器逻辑要尽量小
- 能避免把复杂业务流程塞进触发器

## 适合场景

- 自动维护更新时间
- 写审计记录
- 保持简单派生字段
- 阻止明显违反规则的数据变化

不适合把完整订单流程、支付流程、消息发送流程都藏在触发器里。

## 行级和语句级

| 类型 | 新手解释 |
| --- | --- |
| 行级触发器 | 每影响一行执行一次 |
| 语句级触发器 | 一条 SQL 执行一次 |
| BEFORE | 数据变化前执行 |
| AFTER | 数据变化后执行 |

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| 触发器 | 数据变化时自动执行的机制 |
| 触发函数 | 触发器实际调用的函数 |
| 行级 | 每行触发 |
| 语句级 | 每条语句触发 |

## 练习题

1. 自动维护 `updated_at` 适合用触发器吗？
2. 行级触发器是每条语句一次，还是每行一次？
3. 触发器逻辑应该越复杂越好吗？
4. 为什么复杂业务藏在触发器里会难排查？

::: tip 提示
触发器适合小而稳定的自动逻辑。
:::

::: details 答案
1. 适合。
2. 每行一次。
3. 不是，应该尽量小。
4. 应用代码里不一定能直接看到自动执行的逻辑。
:::

## 常见坑

- 把复杂业务流程塞进触发器
- 触发器之间互相影响
- 批量更新时行级触发器执行次数过多
- 没有文档说明触发器做了什么

## 先记住这三句

- 触发器会自动执行。
- 逻辑越隐藏，排查越难。
- 触发器适合小而稳定的规则。
