# 异常处理

异常处理让 PL/pgSQL 函数在出错时可以给出更明确的处理。它适合处理预期内的小范围错误，不适合吞掉所有问题。

## 你学完能干什么

- 能看懂 `EXCEPTION` 代码块
- 知道什么时候应该处理异常
- 能避免把错误悄悄吞掉
- 能用异常信息帮助调用方定位问题

## 最小例子

```sql
CREATE FUNCTION app.safe_divide(a numeric, b numeric)
RETURNS numeric
LANGUAGE plpgsql
AS $$
BEGIN
  RETURN a / b;
EXCEPTION
  WHEN division_by_zero THEN
    RAISE EXCEPTION '除数不能为 0';
END;
$$;
```

这个函数把数据库底层错误转换成更容易理解的业务错误。

## 什么时候处理

- 错误是预期内的，并且有明确处理方式
- 想把底层错误转成更清楚的提示
- 需要补充上下文再抛出错误
- 少量局部逻辑需要回退

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| 异常 | 执行过程中出现的错误 |
| 捕获 | 用代码处理某类错误 |
| `RAISE` | 主动抛出消息或错误 |
| 吞错 | 捕获错误后不处理也不报告 |

## 练习题

1. `EXCEPTION` 用来处理什么？
2. 捕获异常后完全不提示，为什么危险？
3. `RAISE EXCEPTION` 会继续让调用方知道出错吗？
4. 所有错误都应该在函数里捕获吗？

::: tip 提示
异常处理的目的不是让错误消失，而是让错误更可控、更清楚。
:::

::: details 答案
1. 处理执行中的错误。
2. 调用方会以为成功了，真实问题被隐藏。
3. 会。
4. 不应该，只处理有明确方案的错误。
:::

## 常见坑

- 捕获所有异常后什么都不做
- 把数据质量问题藏在函数内部
- 错误提示太模糊，调用方无法定位
- 用异常处理替代正常条件判断

## 先记住这三句

- 异常处理不是吞错。
- 能提前判断的条件，不一定要靠异常。
- 抛出的错误要让人能定位问题。
