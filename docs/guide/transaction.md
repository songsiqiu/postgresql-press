# 事务与并发

事务解决的是一个很实际的问题：一组数据库操作要么一起成功，要么一起失败。

## 你学完能干什么

- 能知道什么时候应该使用事务
- 能理解 `COMMIT` 和 `ROLLBACK` 的区别
- 能判断为什么两个人同时改数据时会等待
- 能避免把事务开得太久

## 一个最小事务

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

转账就是典型例子。扣款和加款必须一起成功。中间任何一步出错，都应该回滚：

```sql
ROLLBACK;
```

## 为什么会有锁

当两个人同时改同一行数据时，PostgreSQL 必须决定谁先改、谁等待。锁不是异常情况，而是数据库保证数据正确的一部分。

新手可以先记住：

- 读数据通常不会挡住别人读
- 修改同一行数据时可能等待
- 等待太久时要检查事务有没有长时间不提交
- 不要在事务里做太多和数据库无关的事情

## 什么是可见性

PostgreSQL 使用多版本并发控制。简单说，一个事务看到的数据，可能和另一个事务正在修改但还没提交的数据不同。

这能让读写更少互相阻塞，但也意味着你要理解“提交之前，别人不一定看得到你的修改”。

## 新手建议

- 事务尽量短
- 出错时明确回滚
- 批量修改前先用 `SELECT` 确认范围
- 遇到等待，先查有没有长事务

## 动手区：模拟一次转账

假设账户表现在是这样：

| id | owner | balance |
| --- | --- | --- |
| 1 | Alice | 500 |
| 2 | Bob | 200 |

执行：

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

提交后的结果：

| id | owner | balance |
| --- | --- | --- |
| 1 | Alice | 400 |
| 2 | Bob | 300 |

如果把最后一行改成 `ROLLBACK`，两条更新都会撤回，余额仍然是 500 和 200。

## 容易混淆的词

| 词 | 一句话解释 |
| --- | --- |
| 事务 | 一组要一起成功或一起失败的操作 |
| 提交 | 确认这组操作生效 |
| 回滚 | 放弃这组还没提交的操作 |
| 锁 | 数据库为了避免多人同时乱改而做的等待控制 |
| 可见性 | 一个事务能不能看到另一个事务还没提交的修改 |

## 练习题

1. 写出开启事务的 SQL。
2. 两条更新都成功后，应该执行 `COMMIT` 还是 `ROLLBACK`？
3. 如果第二条更新失败，应该执行什么？
4. 为什么不建议在事务里停留很久？
5. 修改一批数据前，为什么要先查命中范围？

::: tip 提示
把事务想成“先临时改，确认没问题再保存”。没有提交前，很多修改都还可以撤回。
:::

::: details 答案
1. `BEGIN;`
2. 执行 `COMMIT;`
3. 执行 `ROLLBACK;`
4. 长事务可能持有锁，也可能让别人等待，还会影响数据库清理旧版本数据。
5. 先确认条件没有写错，避免误改不该改的数据。
:::

## 常见坑

- 开了事务后忘记提交或回滚
- 在事务里等待用户操作、调用慢接口或做无关计算
- 以为读写冲突都是数据库坏了，其实很多是锁等待

## 先记住这三句

- 事务保护一组操作的一致性。
- 能快点提交就不要拖着事务。
- 看到等待，先怀疑长事务和锁。
