# 存储与并发

PostgreSQL 既要保存数据，也要允许很多人同时读写。存储和并发就是理解它稳定性的基础。

## 你学完能干什么

- 知道数据不是只存在“表”这个抽象概念里
- 能理解为什么更新数据会产生旧版本
- 能把 MVCC 和事务可见性联系起来

## 表、行和版本

新手可以先这样理解：

- 表是逻辑上的数据集合
- 行是表里的记录
- 更新一行时，PostgreSQL 会保留必要的旧版本信息
- 不同事务看到哪个版本，取决于事务时间点和隔离规则

## MVCC 是什么

MVCC 可以理解成“多版本并发控制”。它让读和写尽量少互相阻塞。

比如一个事务正在修改某行但还没提交，另一个事务可能仍然能看到修改前的版本。

## 图解：一行被更新后发生什么

```text
更新前：
notes(id=1, body='old')

事务 A 更新但未提交：
旧版本：body='old'   仍可能给其他事务读取
新版本：body='new'   先对事务 A 可见

事务 A 提交后：
新事务通常看到 body='new'
旧版本等待清理条件满足后再清理
```

这就是为什么 PostgreSQL 的更新不只是“原地覆盖”。旧版本还可能被正在运行的事务需要。

## 为什么会这样

如果读写都互相等待，系统会很容易卡住。MVCC 的做法是让读者尽量读到自己应该看到的版本，让写者继续写新版本。代价是旧版本需要后续清理，长事务会拖慢这个清理过程。

## 练习题

1. MVCC 的中文可以怎么理解？
2. 为什么一个事务不一定能看到另一个事务未提交的修改？
3. 长事务为什么可能影响数据库清理旧版本？

::: tip 提示
先把 MVCC 理解为“同一行在一段时间内可能有多个可见版本”。
:::

::: details 答案
1. 多版本并发控制。
2. 数据库要保证事务隔离，未提交的数据通常不能随便让别人看到。
3. 因为旧版本可能还要被长事务读取，数据库不能立刻清理。
:::

## 常见坑

- 以为更新就是原地覆盖，没有旧版本
- 长事务一直开着，影响清理和性能
- 把锁等待和 MVCC 混成一件事
- 看到表变大，只看插入量，不看更新和旧版本

## 先记住这三句

- PostgreSQL 用多版本来减少读写互相阻塞。
- 未提交的数据不一定对别人可见。
- 长事务会让旧版本更难清理。
