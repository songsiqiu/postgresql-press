# 检查点与后台写入

检查点和后台写入都和数据落盘有关。新手先知道它们影响恢复时间、写入压力和系统稳定性即可。

## 你学完能干什么

- 知道检查点大概做什么
- 能理解为什么写入压力可能突然升高
- 知道后台写入和 WAL 不是一回事
- 能把检查点和恢复时间联系起来

## 检查点是什么

PostgreSQL 修改数据时，不一定马上把所有数据页写回磁盘。检查点会让数据库在某个时刻推进“已持久化到足够安全的位置”。

简化理解：

1. 变更先写 WAL
2. 数据页逐步写回磁盘
3. 检查点记录一个恢复可以参考的位置

## 后台写入是什么

后台写入进程会提前把一些脏数据页写回磁盘，减少后续集中写入压力。

如果后台写入跟不上，检查点时可能出现更明显的写入压力。

## 图解：WAL、脏页和检查点

```text
事务修改数据
  |
  v
先写 WAL
  |
  v
内存里的数据页变成脏页
  |
  v
后台写入逐步写回一部分脏页
  |
  v
检查点推进恢复参考位置
```

## 为什么会这样

如果每次修改都立刻把所有数据页同步到磁盘，写入会很慢。PostgreSQL 先用 WAL 保证可恢复，再把数据页逐步写回，兼顾性能和可靠性。

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| WAL | 变更日志 |
| 脏页 | 内存里被改过但还没写回磁盘的数据页 |
| 检查点 | 推进恢复参考位置的一次同步过程 |
| 后台写入 | 提前把部分脏页写回磁盘的后台工作 |

## 练习题

1. 检查点和恢复有什么关系？
2. WAL 和后台写入是一回事吗？
3. 什么是脏页？
4. 为什么检查点期间可能有写入压力？

::: tip 提示
先把 WAL 理解成变更记录，把检查点理解成恢复路标。
:::

::: details 答案
1. 检查点决定恢复时可以从较新的安全位置开始。
2. 不是。WAL 是日志，后台写入负责写数据页。
3. 内存里被改过但还没写回磁盘的数据页。
4. 需要把一定数量的数据页写回磁盘。
:::

## 常见坑

- 把 WAL 写入和数据页写入混成一件事
- 只看 SQL，不看磁盘写入压力
- 不了解检查点对恢复时间的影响
- 检查点过于集中时，只怪 SQL，不看写入压力

## 先记住这三句

- WAL 记录变化，检查点推进恢复位置。
- 后台写入帮助平滑写入压力。
- 写入性能也和磁盘与检查点有关。
