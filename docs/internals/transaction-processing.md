# 事务处理

事务处理解释 PostgreSQL 如何让一组操作一起成功或失败，并在并发访问时保持可理解的结果。

## 你学完能干什么

- 能把 `BEGIN`、`COMMIT`、`ROLLBACK` 和内部事务状态联系起来
- 知道提交不是简单“写一行数据”
- 能理解 WAL、MVCC、锁都和事务处理有关

## 可运行例子

```sql
BEGIN;

UPDATE accounts
SET balance = balance - 100
WHERE id = 1;

UPDATE accounts
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

这段 SQL 的重点不是“两条更新”，而是它们被放进同一个事务：要么都生效，要么在出错时一起放弃。

## 图解：事务提交前后

```text
BEGIN
  |
  v
执行多条修改，产生行版本和 WAL
  |
  v
COMMIT
  |
  v
提交记录写入 WAL，其他事务按规则看到结果
```

## 为什么会这样

事务要保证“这组操作一起算数”。PostgreSQL 通过事务状态、WAL、MVCC 和锁共同维护这个边界，所以提交不是简单改一个字段，而是让一组变化变成对外可见且可恢复的结果。

## 容易混淆的词

| 词 | 区别 |
| --- | --- |
| 事务 | 一组一起成功或失败的操作 |
| WAL | 帮助事务提交后可恢复的日志 |
| MVCC | 控制不同事务看到哪个版本 |
| 锁 | 避免并发修改互相破坏 |
| 保存点 | 事务内部的局部回退位置 |

## 练习题

1. `COMMIT` 表示什么？
2. `ROLLBACK` 会保留事务里的修改吗？
3. 为什么转账例子要放在同一个事务里？

::: tip 提示
事务处理不只关心“能不能写入”，还关心“失败时能不能恢复到正确状态”。
:::

::: details 答案
1. 确认事务里的修改生效。
2. 不会，它会放弃当前事务里的修改。
3. 因为扣款和加款必须一起成功或一起失败。
:::

## 常见坑

- 只写多条 SQL，却没有明确事务边界
- 出错后继续复用已经失败的事务
- 把事务提交和数据立刻写入磁盘细节混为一谈
- 应用认为一条 SQL 成功就等于整个业务动作成功

## 先记住这三句

- 事务边界决定一组操作是否一起生效。
- WAL、MVCC、锁共同支撑事务可靠性。
- 转账这类操作必须放在同一个事务里。
