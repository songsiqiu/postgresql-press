# 锁与等待

锁不是数据库出错，而是数据库在保护数据一致性。真正需要排查的是“谁在等谁、为什么等这么久”。

## 你学完能干什么

- 知道锁为什么存在
- 能区分正常短暂等待和异常长等待
- 能理解长事务为什么容易造成阻塞
- 能把锁等待和事务边界联系起来

## 为什么需要锁

当两个事务同时修改同一行数据时，数据库不能让它们随便覆盖彼此。锁会让其中一个事务等待，直到另一个事务提交或回滚。

简化场景：

1. 事务 A 更新 `accounts.id = 1`
2. 事务 A 还没提交
3. 事务 B 也想更新同一行
4. 事务 B 等待事务 A 结束

## 等待不一定是坏事

短暂等待很正常。问题通常出在：

- 事务 A 开太久
- 应用拿着事务去等外部接口
- 批量更新范围太大
- 手动操作开了事务忘记提交

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| 锁 | 控制并发访问的机制 |
| 等待 | 一个事务暂时不能继续，需要等另一个事务结束 |
| 阻塞者 | 让别人等待的事务 |
| 被阻塞者 | 正在等待的事务 |
| 死锁 | 多个事务互相等，谁都无法继续 |

## 练习题

1. 锁的主要目的是什么？
2. 为什么长事务容易造成等待？
3. 等待一定说明数据库坏了吗？
4. 批量更新前为什么要确认范围？

::: tip 提示
看到“卡住不动”，先想锁等待和长事务，不要立刻重启数据库。
:::

::: details 答案
1. 保护并发读写下的数据一致性。
2. 它持有锁的时间更久，别人就可能等更久。
3. 不一定，短暂等待是正常并发控制。
4. 范围太大可能锁住大量数据，影响其他事务。
:::

## 常见坑

- 在事务里等待用户确认或外部接口
- 手动 `BEGIN` 后忘记 `COMMIT` 或 `ROLLBACK`
- 批量更新没有先查范围

## 先记住这三句

- 锁是保护机制，不是错误本身。
- 长事务是锁等待的常见来源。
- 先找谁阻塞了谁，再决定怎么处理。
