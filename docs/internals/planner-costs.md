# 规划器与代价

PostgreSQL 执行 SQL 前，会先规划怎么执行。规划器会根据统计信息和代价估算，选择它认为更合适的路线。

## 你学完能干什么

- 知道为什么数据库不一定按你想的方式查
- 能理解执行计划和统计信息的关系
- 知道代价是估算，不是实际毫秒数
- 能把慢查询和规划器选择联系起来

## 规划器做什么

面对一条 SQL，PostgreSQL 可能有多种执行方式：

- 顺序扫描整张表
- 使用某个索引
- 先过滤再排序
- 先关联 A 表再关联 B 表

规划器会估算这些方案的成本，然后选一个计划。

## 代价是什么

执行计划里的 cost 是估算单位，不是时间。它表示数据库认为这个步骤大概有多“贵”。

```sql
EXPLAIN
SELECT id, title
FROM notes
WHERE user_id = 10;
```

如果统计信息不准，规划器可能低估或高估数据量，选错路线。

## 统计信息为什么重要

统计信息告诉 PostgreSQL：

- 表大概有多少行
- 某列值分布大概怎样
- 条件可能命中多少数据

这些信息会影响它是否使用索引、怎么做关联、怎么排序。

## 图解：规划器怎么选路线

```text
SQL
  |
  v
候选路线：顺序扫描 / 索引扫描 / 不同关联顺序
  |
  v
参考统计信息估算行数和成本
  |
  v
选择总代价较低的计划
```

## 为什么会这样

数据库无法真的把所有路线都执行一遍再选最快的，那会太贵。所以它依赖统计信息做估算。统计信息越接近真实数据分布，计划越可能合理。

## 练习题

1. cost 是实际执行时间吗？
2. 统计信息不准可能造成什么问题？
3. 为什么同一条 SQL 在数据量变化后计划会变？
4. 看慢查询时为什么要看执行计划？

::: tip 提示
执行计划是数据库选择的路线图。慢查询先看路线，再判断怎么改。
:::

::: details 答案
1. 不是，是规划器的估算单位。
2. 可能选错执行计划。
3. 数据量和分布变了，估算成本也会变。
4. 否则不知道数据库实际选择了哪条执行路线。
:::

## 常见坑

- 把 cost 当成毫秒
- 不看统计信息，直接怪索引
- 只看 SQL 文本，不看执行计划
- 大量导入后不更新统计信息，却抱怨计划不准

## 先记住这三句

- 规划器负责选执行路线。
- cost 是估算，不是时间。
- 统计信息会影响计划选择。
