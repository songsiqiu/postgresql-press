# 错误处理与重试

应用访问数据库时，错误不可避免。关键不是“永远不出错”，而是能分清哪些错误可以重试，哪些必须修数据或修代码。

## 你学完能干什么

- 能区分语法错误、权限错误、约束错误和并发冲突
- 知道哪些错误不应该盲目重试
- 能给接口错误保留足够定位信息
- 能理解重试必须有边界

## 常见错误类型

| 类型 | 可能原因 | 处理思路 |
| --- | --- | --- |
| 语法错误 | SQL 写错 | 修 SQL |
| 权限错误 | 角色权限不够 | 查授权和连接用户 |
| 约束错误 | 数据违反主键、唯一、外键等约束 | 修输入或业务逻辑 |
| 连接错误 | 网络、地址、认证、连接数问题 | 查连接配置和服务状态 |
| 并发冲突 | 多个事务同时修改相关数据 | 评估重试或调整事务 |

## 哪些错误可以重试

可以考虑重试的，通常是临时问题，比如短暂连接失败、可恢复的并发冲突。

不应该盲目重试的：

- SQL 语法错误
- 权限错误
- 唯一约束冲突
- 外键约束冲突

这些错误重试多少次也大概率不会自己变好。

## 记录错误时保留什么

- 接口名或业务动作
- 数据库错误信息
- 发生时间
- 当前用户或请求标识
- SQL 名称或调用点
- 关键参数，但不要记录密码等敏感信息

## 练习题

1. 唯一约束冲突应该盲目重试吗？
2. 权限错误通常要查什么？
3. 为什么错误日志不能记录密码？
4. 并发冲突为什么有时可以重试？

::: tip 提示
先判断错误类型，再决定修 SQL、补权限、改数据，还是有限重试。
:::

::: details 答案
1. 不应该，应该修输入或业务逻辑。
2. 当前连接用户、角色权限、对象权限。
3. 密码属于敏感信息，日志泄露会带来安全风险。
4. 因为冲突可能是瞬时的，稍后重试可能成功，但要限制次数。
:::

## 常见坑

- 所有数据库错误都自动重试
- 日志里没有接口名和时间，后续查不到
- 把数据库原始错误吞掉，只返回“系统异常”
- 在日志里记录敏感信息

## 先记住这三句

- 错误先分类，再处理。
- 不是所有错误都能靠重试解决。
- 日志要能定位问题，也要保护敏感信息。
