# 预处理语句与参数

预处理语句和参数绑定是应用安全访问数据库的基础。它们能减少 SQL 注入风险，也能让数据库更稳定地处理重复语句。

## 你学完能干什么

- 知道为什么不能拼接用户输入
- 能理解参数绑定的基本思路
- 能区分 SQL 结构和参数值
- 知道预处理不是所有性能问题的答案

## 错误思路：拼接 SQL

```text
SELECT *
FROM users
WHERE name = '用户输入';
```

如果用户输入被直接拼进 SQL，可能导致 SQL 注入，也可能因为引号等字符让语句出错。

## 正确思路：参数绑定

```text
SELECT *
FROM users
WHERE name = $1;
```

`$1` 是占位符，真实值由数据库驱动绑定进去。

## SQL 结构和参数值

| 部分 | 例子 | 说明 |
| --- | --- | --- |
| SQL 结构 | `WHERE name = $1` | 稳定的查询形状 |
| 参数值 | `Alice` | 每次执行传入的具体值 |

## 什么时候有帮助

- 用户输入参与查询
- 同一类 SQL 重复执行
- 希望应用层 SQL 更清楚
- 需要减少注入风险

## 练习题

1. `$1` 在参数化 SQL 中表示什么？
2. 为什么不能直接拼接用户输入？
3. 预处理语句能替代索引优化吗？
4. 参数绑定主要保护 SQL 的哪一部分？

::: tip 提示
先把 SQL 结构固定下来，再把用户输入作为参数传入。
:::

::: details 答案
1. 第一个参数占位符。
2. 可能造成 SQL 注入或语法错误。
3. 不能，它解决的是参数绑定和重复执行问题，不替代索引和执行计划分析。
4. 保护 SQL 结构不被用户输入破坏。
:::

## 常见坑

- 只在部分接口用参数绑定，其他地方仍然拼接
- 把表名、列名也当普通参数随便绑定
- 以为用了预处理就不需要索引和执行计划

## 先记住这三句

- 用户输入不要拼进 SQL。
- 参数绑定把 SQL 结构和值分开。
- 预处理有帮助，但不是万能性能优化。
