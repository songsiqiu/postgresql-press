# ECPG：C 里的嵌入式 SQL

`ECPG` 让 C 程序可以写嵌入式 SQL，再经过预处理变成可编译的 C 代码。

## 你学完能干什么

- 知道 `ECPG` 和普通驱动的区别
- 能理解“嵌入式 SQL”是什么意思
- 知道它更适合哪些历史系统或底层程序

## 可运行例子

普通驱动通常是这样调用：

```text
在 C 代码里调用函数，函数参数里放 SQL
```

`ECPG` 的思路更像这样：

```sql
EXEC SQL SELECT name INTO :user_name FROM demo_users WHERE id = 1;
```

这不是给 `psql` 直接执行的 SQL，而是写在 C 源码里的嵌入式 SQL，需要先经过 `ecpg` 预处理。

## 容易混淆的词

| 词 | 区别 |
| --- | --- |
| `ECPG` | 嵌入式 SQL 预处理器 |
| `libpq` | C 客户端连接库 |
| 嵌入式 SQL | 写在宿主语言代码里的 SQL |
| 预处理 | 编译前先把嵌入式 SQL 转成普通代码 |

## 练习题

1. `ECPG` 里的 SQL 是直接交给 `psql` 执行的吗？
2. `ECPG` 和 `libpq` 哪个更偏“预处理器”？
3. 为什么新项目通常先考虑语言驱动，而不是直接从 `ECPG` 开始？

::: tip 提示
看到 `EXEC SQL`，先判断它是不是写在 C 程序里的嵌入式 SQL。
:::

::: details 答案
1. 不是，它写在 C 源码中，需要预处理。
2. `ECPG`。
3. 语言驱动更贴近日常开发生态，学习和维护成本通常更低。
:::

## 常见坑

- 把 `EXEC SQL` 当作普通 SQL 命令
- 忽略预处理这一步
- 在新手阶段过早深入历史系统接口

## 先记住这三句

- `ECPG` 是 C 里的嵌入式 SQL 方案。
- 它需要预处理，不是普通 SQL 脚本。
- 普通应用开发先学连接串、驱动、事务边界更实用。
