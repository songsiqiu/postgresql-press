# 读写分离

读写分离常用于有主库和只读副本的系统。它能分担读取压力，但会带来延迟、一致性和事务边界问题。

## 你学完能干什么

- 知道哪些请求适合走只读副本
- 能理解复制延迟带来的“刚写完读不到”
- 知道事务里的读写不要随意拆开
- 能判断什么时候应该强制读主库

## 基本做法

常见应用会把请求分成两类：

- 写入、更新、删除：走主库
- 普通列表、报表、低一致性查询：可以走只读副本

但如果用户刚提交订单后立刻查看详情，通常应该读主库，避免副本还没同步导致“刚写完看不到”。

## 一个判断表

| 场景 | 建议 |
| --- | --- |
| 创建订单后立即查订单详情 | 读主库 |
| 后台统计昨天数据 | 可读副本 |
| 修改资料后立刻回显 | 读主库 |
| 大报表导出 | 可读副本，但要接受延迟 |

## 应用里怎么写

可以在代码里显式区分读主库和读副本：

```js
async function getOrderAfterCreate(orderId) {
  return primaryDb.query(
    'SELECT id, status, total_amount FROM orders WHERE id = $1',
    [orderId]
  )
}

async function getYesterdayReport() {
  return replicaDb.query(
    'SELECT status, count(*) FROM orders WHERE created_at >= CURRENT_DATE - 1 GROUP BY status'
  )
}
```

不要把所有 `SELECT` 都自动丢给副本。刚写完要读自己的结果，优先读主库。

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| 主库 | 接受写入的数据库 |
| 只读副本 | 从主库复制数据，通常只读 |
| 复制延迟 | 副本落后主库的时间 |
| 读写分离 | 把读和写分发到不同数据库实例 |

## 练习题

1. 写入请求应该走主库还是只读副本？
2. 刚写完马上查询，为什么可能不能读副本？
3. 昨天的统计报表通常能不能考虑读副本？
4. 读写分离能不能自动解决所有性能问题？

::: tip 提示
判断读哪里，先问一句：这个请求能不能接受短暂延迟。
:::

::: details 答案
1. 主库。
2. 副本可能还没同步到最新数据。
3. 通常可以。
4. 不能。
:::

## 常见坑

- 刚写完就读副本，用户看到旧数据
- 事务里一半读主库、一半读副本
- 把所有慢查询都丢给副本，不优化 SQL
- 没有监控复制延迟
- 没给“必须读新数据”的接口做主库白名单

## 先记住这三句

- 读写分离会带来一致性问题。
- 刚写完要谨慎读副本。
- 副本分担压力，不替代 SQL 优化。
