# 回归测试

PostgreSQL 官方文档里的回归测试，主要用于验证数据库功能在构建、安装或修改后是否仍然正常。

## 你学完能干什么

- 知道回归测试解决什么问题
- 能区分数据库内核测试和业务系统测试
- 知道什么时候需要关注官方回归测试

## 可运行例子

如果你只是使用 PostgreSQL，一般不会每天跑官方回归测试。它更常见于这些场景：

```text
从源码编译 PostgreSQL -> 运行测试 -> 确认构建结果可靠
```

业务项目自己的测试则应该验证业务表、接口、迁移脚本和关键 SQL 是否符合预期。

## 操作步骤：业务侧最小回归

升级 PostgreSQL 或改迁移脚本前，业务项目至少验证：

```text
能连接数据库
关键迁移能执行
核心查询结果正确
事务失败能回滚
备份恢复流程没有被破坏
```

这和 PostgreSQL 官方源码回归测试不是一回事。官方测试证明数据库本身，业务回归证明你的系统使用方式没坏。

## 容易混淆的词

| 词 | 区别 |
| --- | --- |
| 回归测试 | 确认已有能力没有被改坏 |
| 单元测试 | 验证较小范围的代码或逻辑 |
| 集成测试 | 验证多个模块一起工作 |
| 迁移测试 | 验证数据库结构变更能正确执行 |

## 练习题

1. 官方回归测试更常见于源码使用者，还是普通 SQL 学习者？
2. 回归测试主要防止什么问题？
3. 业务项目需要只依赖 PostgreSQL 官方回归测试吗？

::: tip 提示
官方回归测试验证 PostgreSQL 本身；业务测试验证你的系统怎么使用 PostgreSQL。
:::

::: details 答案
1. 源码使用者或数据库开发者。
2. 防止已有功能被改坏。
3. 不需要。业务项目要写自己的数据库迁移和关键流程测试。
:::

## 常见坑

- 把官方回归测试当成业务测试
- 数据库升级前不验证业务关键 SQL
- 只看测试是否通过，不看测试环境是否接近真实环境
- 只测应用接口，不测数据库迁移脚本

## 先记住这三句

- 回归测试是防止旧能力被改坏。
- 官方测试验证 PostgreSQL 本身。
- 业务系统还要验证自己的表、数据和流程。
