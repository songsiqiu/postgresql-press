# 时间点恢复

时间点恢复可以把数据库恢复到某个历史时间点。它通常依赖基础备份和 WAL，不是只有一个备份文件就能完成。

## 你学完能干什么

- 知道时间点恢复解决什么问题
- 能理解基础备份和 WAL 的关系
- 知道恢复目标可以是时间、事务或恢复点
- 能意识到必须提前演练

## 什么时候需要

- 误删了重要数据
- 错误脚本在某个时间点执行
- 需要恢复到事故发生前
- 测试历史状态

时间点恢复的核心是：先恢复一个基础备份，再重放 WAL 到指定位置。

## 基本材料

| 材料 | 用途 |
| --- | --- |
| 基础备份 | 提供恢复起点 |
| WAL 归档 | 提供备份之后的变更记录 |
| 恢复目标 | 决定重放到哪里停止 |
| 恢复演练 | 验证流程真的可用 |

## 操作步骤：确定恢复目标

事故发生后，不要立刻恢复到“当前”。先收集：

1. 事故大概发生时间。
2. 错误 SQL 或错误操作开始时间。
3. 最后一次确认数据正常的时间。
4. 基础备份和 WAL 是否覆盖这个时间点。

恢复目标通常选在错误操作之前，而不是用户发现事故的时间。

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| PITR | 时间点恢复 |
| 基础备份 | 某个时间点的数据副本 |
| WAL 重放 | 按日志重新应用变更 |
| 恢复目标 | 恢复停止的位置 |

## 练习题

1. 时间点恢复通常只靠一个基础备份够吗？
2. WAL 在时间点恢复里起什么作用？
3. 为什么要做恢复演练？
4. 误删数据后，恢复目标应该选在误删前还是误删后？

::: tip 提示
能恢复到哪里，取决于备份和 WAL 是否完整。
:::

::: details 答案
1. 通常不够，还需要 WAL。
2. 提供备份之后的变更记录，让数据库能重放到目标位置。
3. 证明备份和流程真的能用。
4. 误删前。
:::

## 常见坑

- 只做备份，不保存 WAL 归档
- 从未演练恢复流程
- 事故后才发现恢复目标不明确
- 把高可用当成时间点恢复
- 恢复到发现事故的时间，结果把错误操作也恢复进去了

## 先记住这三句

- 时间点恢复依赖基础备份和 WAL。
- 没演练的备份不可靠。
- 恢复目标要在事故点之前。
