# 连接限制

连接限制决定数据库能同时接多少连接。它不是越大越好，连接太多反而会拖垮数据库。

## 你学完能干什么

- 能理解 `max_connections` 的作用
- 知道连接池为什么要限制大小
- 能区分数据库连接数和应用并发数
- 能判断连接打满时该看哪些方向

## 为什么不能无限加

每个数据库连接都会占用内存和调度资源。连接数太多时，即使 SQL 不复杂，也可能因为上下文切换、内存压力和锁等待让系统变慢。

常见配置方向：

- 数据库设置总连接上限
- 应用连接池设置池大小
- 不同应用角色分配不同连接预算
- 监控活跃连接和空闲连接

## 常见排查

```sql
SELECT state, count(*)
FROM pg_stat_activity
GROUP BY state
ORDER BY count(*) DESC;
```

这条 SQL 可以先看连接大致分布：活跃、空闲、事务中空闲等。

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| `max_connections` | 数据库允许的最大连接数 |
| 连接池大小 | 应用侧最多保留多少数据库连接 |
| 活跃连接 | 正在执行任务的连接 |
| 空闲连接 | 暂时没在执行 SQL 的连接 |
| 事务中空闲 | 开着事务但当前没执行 SQL，风险更高 |

## 练习题

1. `max_connections` 是越大越好吗？
2. 应用连接池为什么也要限制大小？
3. `idle in transaction` 为什么值得关注？
4. 查看连接状态可以先看哪个系统视图？

::: tip 提示
连接数问题先看“谁占着连接”和“占着连接时在做什么”。
:::

::: details 答案
1. 不是。
2. 避免应用把数据库连接资源占满。
3. 它可能持有事务和锁，影响清理和其他请求。
4. `pg_stat_activity`。
:::

## 常见坑

- 数据库连接打满后只调大上限
- 每个应用实例都开很大的连接池
- 空闲事务长期不提交
- 不区分后台任务和在线请求的连接预算

## 先记住这三句

- 连接是资源，不是越多越好。
- 连接池也要有上限。
- 看到连接打满，先查连接状态。
