# 逻辑复制基础

逻辑复制按数据变化来同步表级内容。它和物理复制不同，更适合部分表同步、数据迁移和跨版本场景。

## 你学完能干什么

- 知道逻辑复制和物理复制的大致区别
- 能理解发布和订阅的基本关系
- 知道逻辑复制不等于完整高可用方案
- 能列出使用前要确认的条件

## 发布和订阅

逻辑复制常用两个概念：

| 概念 | 新手解释 |
| --- | --- |
| 发布 | 源端声明哪些表的变化要发出去 |
| 订阅 | 目标端接收这些变化 |

可以先理解成：源库发布，目标库订阅。

## 适合什么

- 只同步部分表
- 平滑迁移数据
- 做跨版本或跨环境数据同步
- 把业务数据同步给分析库

## 不适合什么

- 替代完整备份
- 没有主键或唯一标识却频繁更新的表
- 对所有对象、权限、DDL 都自动完整同步的期待

## 操作步骤：检查发布和订阅

源库看发布：

```sql
SELECT pubname, puballtables, pubinsert, pubupdate, pubdelete
FROM pg_publication;
```

目标库看订阅：

```sql
SELECT subname, subenabled, subslotname
FROM pg_subscription;
```

如果同步异常，再查复制槽是否活跃、目标端是否报错、表是否有可识别行的主键或复制标识。

## 练习题

1. 逻辑复制常见的两个核心概念是什么？
2. 它适合同步部分表吗？
3. 逻辑复制能替代备份吗？
4. 为什么要关注表是否有主键？

::: tip 提示
逻辑复制更像“按表同步数据变化”，不要把它想成完整复制整个数据库的一切。
:::

::: details 答案
1. 发布和订阅。
2. 适合。
3. 不能。
4. 更新和删除时需要可靠识别具体行。
:::

## 常见坑

- 以为逻辑复制会自动同步所有 DDL 和权限
- 没有主键的表也直接拿来高频更新同步
- 把逻辑复制当备份方案
- 源端改了表结构，目标端没有同步调整

## 先记住这三句

- 源端发布，目标端订阅。
- 逻辑复制适合部分表和迁移场景。
- 逻辑复制不能替代备份。
