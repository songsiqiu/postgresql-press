# 上线前检查清单

数据库上线前检查不是形式主义。它能提前发现连接、安全、备份、容量和回滚上的风险。

## 你学完能干什么

- 能列出 PostgreSQL 上线前的基础检查项
- 知道备份、权限、连接、监控都要提前确认
- 能避免“能连上就上线”的粗糙做法

## 基础检查项

| 项目 | 要确认什么 |
| --- | --- |
| 连接 | 应用连接信息、连接池大小、超时设置 |
| 权限 | 应用账号不是超级用户，权限够用不过大 |
| 备份 | 已有备份策略，并做过恢复验证 |
| 迁移 | 结构变更可回滚或有补救方案 |
| 监控 | 连接数、磁盘、慢查询、锁等待有观察入口 |
| 日志 | 错误和慢查询能定位到时间和 SQL |
| 容量 | 磁盘和表增长有预估 |
| 安全 | 访问来源、认证方式、密码管理已确认 |

## 上线前最少要问

1. 数据误删能不能恢复？
2. 应用账号权限是不是过大？
3. 连接池会不会打满数据库？
4. 出问题时谁看日志、谁处理回滚？

## 练习题

1. 为什么应用账号不建议用超级用户？
2. 只配置备份但没恢复演练，算安全吗？
3. 为什么上线前要确认连接池大小？
4. 慢查询日志有什么价值？

::: tip 提示
上线检查的目标是减少未知风险，不是追求一张完美表格。
:::

::: details 答案
1. 权限过大，应用出错或泄露时影响范围太大。
2. 不算，备份要能恢复才可靠。
3. 连接池太大可能耗尽数据库连接。
4. 出问题时能定位慢 SQL 和发生时间。
:::

## 常见坑

- 应用直接用超级用户连接
- 没做恢复演练就相信备份
- 没监控磁盘和连接数
- 迁移失败没有处理预案

## 先记住这三句

- 能连上不等于能上线。
- 备份要恢复验证。
- 权限、连接、监控要提前确认。
