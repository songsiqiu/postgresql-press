# pg_stat_statements

`pg_stat_statements` 是排查 SQL 性能时很常用的扩展。它按 SQL 形态汇总执行次数、耗时和读取情况。

## 你学完能干什么

- 知道 `pg_stat_statements` 用来找高频和高耗时 SQL
- 能理解它是按归一化 SQL 汇总
- 知道它需要提前启用
- 能避免只凭单次慢查询判断全局问题

## 能看什么

常见关注点包括：

- SQL 执行次数
- 总耗时和平均耗时
- 读取块数量
- 返回行数
- 是否有明显高频 SQL

示例查询：

```sql
SELECT query, calls, total_exec_time, mean_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

## 适合场景

- 找最耗总时间的 SQL
- 找执行次数异常高的 SQL
- 对比优化前后
- 给慢查询排查提供入口

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| 归一化 SQL | 把参数值抽掉后归为同一类 SQL |
| `calls` | 执行次数 |
| 总耗时 | 多次执行加起来的耗时 |
| 平均耗时 | 单次平均执行耗时 |

## 练习题

1. `pg_stat_statements` 常用于排查什么？
2. `calls` 表示什么？
3. 总耗时高一定等于单次慢吗？
4. 它需要提前启用吗？

::: tip 提示
先看总耗时和执行次数，再决定是高频问题还是单次慢问题。
:::

::: details 答案
1. SQL 性能问题。
2. 执行次数。
3. 不一定，可能是执行次数太多。
4. 需要。
:::

## 常见坑

- 没启用扩展，事故后才想查历史
- 只看平均耗时，不看执行次数
- 只看单条慢 SQL，不看总消耗
- 忘记优化前后记录对比数据

## 先记住这三句

- 它帮你找最值得看的 SQL。
- 总耗时和执行次数要一起看。
- 性能排查要提前留数据。
