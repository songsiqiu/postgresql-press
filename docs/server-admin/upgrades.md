# 版本升级

PostgreSQL 升级不是简单替换程序文件。升级前要确认版本差异、扩展兼容、备份恢复和回滚方案。

## 你学完能干什么

- 知道小版本升级和大版本升级不同
- 能列出升级前检查项
- 知道升级前要做备份和演练
- 不会在生产环境直接临时升级

## 小版本和大版本

| 类型 | 新手理解 |
| --- | --- |
| 小版本升级 | 通常是修复和补丁，风险相对低 |
| 大版本升级 | 可能涉及数据格式、功能变化和兼容性，需要更完整计划 |

大版本升级前尤其要看应用 SQL、扩展、备份、恢复和停机窗口。

## 升级前检查

- 当前版本和目标版本
- 应用是否使用了受影响功能
- 扩展是否兼容
- 是否有可用备份
- 是否做过恢复演练
- 是否有回滚方案
- 是否安排停机或切换窗口

## 升级后验证

- 应用能否连接
- 关键查询是否正常
- 扩展是否可用
- 备份任务是否正常
- 监控和日志是否正常

## 操作步骤：升级前后对照表

升级前记录：

```sql
SELECT version();
SELECT extname, extversion FROM pg_extension ORDER BY extname;
```

准备一组业务关键 SQL，升级后逐条验证。至少包括：

```text
登录或连接
核心列表查询
核心写入事务
报表或统计 SQL
备份任务
恢复演练入口
```

如果大版本升级使用 `pg_upgrade` 或逻辑迁移，也要提前在测试环境完整跑一遍，不要把生产第一次执行当演练。

## 练习题

1. 小版本升级和大版本升级风险一样吗？
2. 升级前为什么要检查扩展？
3. 为什么升级前要做恢复演练？
4. 升级后应该只看服务能启动吗？

::: tip 提示
升级前先在测试环境走一遍。生产环境不要靠现场发挥。
:::

::: details 答案
1. 不一样，大版本升级通常风险更高。
2. 扩展可能不兼容目标版本。
3. 确认出问题时能恢复。
4. 不够，还要验证应用、查询、扩展、备份、监控。
:::

## 常见坑

- 生产环境直接升级，没有演练
- 忽略扩展兼容
- 没有回滚方案
- 升级后只看数据库能启动，不跑业务验证
- 没记录升级前扩展版本，出问题后难对比

## 先记住这三句

- 大版本升级要计划。
- 升级前必须有可用备份。
- 升级后要验证业务路径。
