# WAL 归档

WAL 归档是把预写式日志保存到安全位置。它是时间点恢复和部分备份方案的重要基础。

## 你学完能干什么

- 知道 WAL 归档为什么重要
- 能理解归档和普通日志备份的区别
- 知道归档失败会影响恢复能力
- 能把归档、基础备份和时间点恢复联系起来

## 为什么要归档

基础备份只是某个时间点的数据副本。备份之后发生的变化，需要 WAL 来补上。

如果把 WAL 持续归档保存，就可以在恢复时从基础备份开始，重放 WAL 到目标位置。

## 要关注什么

| 项目 | 为什么重要 |
| --- | --- |
| 归档是否成功 | 失败会造成恢复链断裂 |
| 归档保存多久 | 决定可恢复时间范围 |
| 归档存放位置 | 不能和主库一起丢 |
| 恢复演练 | 验证 WAL 真的可用 |

## 排障步骤：归档失败

1. 先看 PostgreSQL 日志里的归档错误。
2. 确认归档目录或对象存储是否可写。
3. 确认磁盘或存储桶空间是否足够。
4. 确认归档命令是否能在数据库运行用户下执行。
5. 修复后观察新的 WAL 是否能继续归档。

可以查看归档统计：

```sql
SELECT archived_count, failed_count, last_archived_wal, last_failed_wal
FROM pg_stat_archiver;
```

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| WAL | 数据库变更记录 |
| WAL 归档 | 把 WAL 保存到长期位置 |
| 基础备份 | 恢复的起点 |
| 时间点恢复 | 用基础备份和 WAL 恢复到指定位置 |

## 练习题

1. WAL 归档主要服务哪类恢复能力？
2. 基础备份之后的变化靠什么补上？
3. 归档文件应该和主库放在同一个风险位置吗？
4. 只配置归档但从不演练恢复可靠吗？

::: tip 提示
备份看起点，WAL 归档看起点之后的变化。
:::

::: details 答案
1. 时间点恢复。
2. WAL。
3. 不应该。
4. 不可靠。
:::

## 常见坑

- 归档失败没人发现
- WAL 和主库放在同一块容易一起丢的磁盘
- 只保留很短时间，无法覆盖恢复需求
- 从不做恢复演练
- 归档失败后只清理本地 WAL，不修归档链路

## 先记住这三句

- WAL 归档保存变化记录。
- 时间点恢复离不开完整 WAL 链。
- 归档必须监控和演练。
