# 本地化与编码

本地化会影响文本怎么排序、时间怎么显示、字符能不能正确保存。新手先重点理解编码、排序规则和时区。

## 你学完能干什么

- 知道编码决定能保存哪些字符
- 能理解排序规则会影响文本比较
- 知道时区设置会影响时间显示
- 能避免上线后才发现排序和时间不符合预期

## 常见检查

```sql
SHOW server_encoding;
SHOW lc_collate;
SHOW timezone;
```

这些设置不只是显示信息，它们会影响应用看到的数据表现。

## 一个直觉例子

同样是按姓名排序，不同排序规则可能让中文、大小写和带重音字符的顺序不同。

时间也是一样：

```sql
SELECT now();
```

如果会话时区不同，同一个时间点显示出来的本地时间可能不同。

## 操作步骤：迁移前检查本地化口径

```sql
SHOW server_encoding;
SHOW lc_collate;
SHOW lc_ctype;
SHOW timezone;
```

迁移前后分别记录这些值。特别是排序规则不同，可能导致同一条 `ORDER BY` 在新旧环境里顺序不同。

时间问题可以用同一个时间点测试：

```sql
SELECT timestamptz '2026-01-01 00:00:00+00';
```

## 容易混淆的词

| 词 | 新手解释 |
| --- | --- |
| 编码 | 字符如何保存 |
| 排序规则 | 文本如何比较和排序 |
| 区域设置 | 语言和地区相关规则 |
| 时区 | 时间点如何显示成本地时间 |

## 练习题

1. `server_encoding` 主要影响字符保存还是连接数量？
2. 排序规则会不会影响 `ORDER BY name` 的结果？
3. 同一个时间点在不同时区显示会一样吗？
4. 为什么上线前要确认编码和时区？

::: tip 提示
本地化不是翻译界面，它会影响数据库比较、排序和显示。
:::

::: details 答案
1. 影响字符保存。
2. 会。
3. 不一定一样。
4. 避免数据保存、排序和时间显示不符合业务预期。
:::

## 常见坑

- 只看应用时区，不看数据库会话时区
- 忽略排序规则对文本比较的影响
- 迁移时没确认新旧库编码一致
- 把排序规则和字符编码混成一个概念
- 只在应用层设置时区，忽略数据库会话显示

## 先记住这三句

- 编码管字符能不能正确保存。
- 排序规则管文本怎么比较。
- 时区管时间点怎么显示。
