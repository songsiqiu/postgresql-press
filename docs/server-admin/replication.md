# 复制与高可用

复制和高可用解决的是数据库故障时怎么减少影响。它们很重要，但不能替代备份。

## 你学完能干什么

- 知道复制大概解决什么问题
- 能区分读扩展、容灾和备份
- 知道高可用方案需要演练

## 复制是什么

复制可以让一个 PostgreSQL 实例的数据变化同步到另一个实例。常见形式是主库负责写入，从库接收变化。

它常用于：

- 故障切换
- 读请求分担
- 报表或分析隔离
- 灾备准备

## 高可用不等于备份

高可用关注“服务尽量不中断”。备份关注“数据能恢复”。

如果误删了一张表，复制可能很快把这个误删同步到从库。此时仍然需要备份来恢复。

## 演练很重要

高可用方案不能只停留在架构图上。要定期演练：

- 主库故障怎么切换
- 切换后应用怎么连接
- 原主库恢复后怎么处理
- 数据是否一致

## 操作步骤：先看复制是否健康

在主库上看复制发送状态：

```sql
SELECT application_name, state, sync_state, sent_lsn, replay_lsn
FROM pg_stat_replication;
```

在从库上看接收和回放状态：

```sql
SELECT status, receive_start_lsn, latest_end_lsn
FROM pg_stat_wal_receiver;
```

这些视图不是高可用方案本身，但能帮你确认复制链路是不是还活着。

## 排障场景：从库读到旧数据

1. 先确认应用是不是刚写完主库就读从库。
2. 再看从库是否有复制延迟。
3. 对强一致读请求，优先读主库。
4. 对报表和低实时性页面，再考虑读从库。

## 练习题

1. 复制能替代备份吗？
2. 从库常见用途有哪些？
3. 为什么高可用方案需要演练？

::: tip 提示
把高可用理解成“少停机”，把备份理解成“能找回”。
:::

::: details 答案
1. 不能。
2. 故障切换、读请求分担、报表隔离、灾备。
3. 故障时步骤复杂，不演练就不知道是否真的能切换成功。
:::

## 常见坑

- 以为有从库就不用备份
- 只画架构图，从不做切换演练
- 忽略应用连接地址和故障切换流程
- 刚写完数据就读从库，用户看到旧结果

## 先记住这三句

- 复制不是备份。
- 高可用要靠演练证明。
- 故障切换要同时考虑数据库和应用。
