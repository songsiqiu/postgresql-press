# 日志与排障

数据库出问题时，日志通常是第一现场。这一页先帮新手知道该看什么、怎么描述问题。

## 你学完能干什么

- 知道日志能帮助定位哪些问题
- 能区分连接失败、慢查询、锁等待和权限错误
- 能用更清楚的话把问题转给后端或运维
- 不会一看到报错就盲目改配置

## 先看哪些信息

排查 PostgreSQL 问题时，先收集这几类信息：

| 信息 | 说明 |
| --- | --- |
| 时间 | 问题发生的准确时间 |
| 用户 | 哪个数据库用户在操作 |
| 数据库 | 连接到了哪个数据库 |
| SQL | 出问题的语句或接口触发的语句 |
| 错误信息 | PostgreSQL 返回的原始错误 |

## 常见问题分类

### 连接失败

先看地址、端口、用户名、密码、数据库名是否正确，再看访问控制配置。

### 权限错误

常见现象是能连上数据库，但读写某张表时报错。此时要看角色有没有对应对象的权限。

### 慢查询

先拿到慢 SQL 和参数，再看执行计划。不要只凭接口慢就直接加索引。

### 锁等待

如果某条修改语句一直不结束，可能是在等另一个事务释放锁。

## 排障步骤：接口突然变慢

可以按这个顺序查，不要一上来就改参数：

1. 确认慢的接口、发生时间、数据库名和连接用户
2. 找到对应 SQL 和关键参数
3. 用 `EXPLAIN` 或 `EXPLAIN ANALYZE` 看执行计划
4. 看是否有锁等待、连接打满或磁盘压力
5. 再决定是改 SQL、补索引、更新统计信息，还是调整资源

## 排障步骤：能连上但查不了表

```sql
SELECT current_user;

SELECT has_table_privilege(current_user, 'public.notes', 'SELECT');
```

如果连接用户对表没有 `SELECT` 权限，问题就不是“连不上”，而是授权不足。接下来应该检查角色、模式权限和表权限。

## 练习题

1. 排查问题时，为什么要记录准确时间？
2. “能连接数据库，但查询某张表失败”更像连接问题还是权限问题？
3. 慢查询应该先拿到哪些信息？

::: tip 提示
把问题拆成“连不上、没权限、查得慢、改不动”四类，会比只说“数据库坏了”更容易定位。
:::

::: details 答案
1. 方便在日志里定位同一时间段发生了什么。
2. 更像权限问题。
3. SQL、参数、表数据量、执行计划、发生时间。
:::

## 常见坑

- 只截图前端报错，不保留数据库原始错误
- 没有记录发生时间，导致日志难找
- 慢查询不看执行计划就直接改索引
- 能连上数据库后，还把所有失败都归类成连接问题

## 先记住这三句

- 日志是排查问题的入口。
- 先分类，再定位。
- 慢查询要看 SQL 和执行计划。
